| TP-046 | 2026-09-29 | Elo, same-week rule: a player's Elo never changes within a week. | TP-047 | 2026-09-29 | Lock Week automation (Tom's option c): a Tuesday 9 AM email reminds the admin(s) if last week still isn't locked. Wednesday, immediately before that week's draft is built, the prior week auto-locks if every set has been entered; otherwise the admins get an email listing the empty sets and the draft is built on the older (unlocked) Elo. Unlock is offered only for the **most recent** locked week, only while the next week's status is still `draft`/`availability_open` (i.e. its pairings haven't been built from this Elo), and aborts the whole unlock if any affected player's `currentElo` no longer matches what the lock recorded | Building the next week's pairings on stale Elo would be silently wrong if the prior week weren't locked in time; restricting unlock to the most recent week, not-yet-built-on state keeps "undo a lock" from ever contradicting Elo that's already been used |
| TP-048 | 2026-09-29 | Lock and unlock run inside a Firestore **transaction**, not a re-read-then-batch. A manual admin lock and the Wednesday auto-lock can overlap (the admin taps Lock right as `weeklyAutomation` runs); a plain re-read guard before a batch write can't stop both from passing the check and applying every player's Elo delta twice. A transaction's reads become its own write-conflict check — if the week (or anything else it read) changed between the read and the commit, Firestore aborts and retries the whole callback, so a losing concurrent attempt re-reads the now-locked week and is refused instead of double-applying | A re-read guard only catches a conflict that already happened *before* the guard's own read; it can't catch one that happens between that read and the write that follows it. A transaction's built-in retry-on-conflict closes exactly that gap |
